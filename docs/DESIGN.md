# ThesisForge 设计文档

> 日期：2026-10-15
> 状态：v1 设计稿（待 builder 检查）

## 1. 项目概述

**ThesisForge** 是一个开源的后台管理系统框架，核心卖点是内置"AI 定制"能力：用户通过网页里嵌入的 OpenCode（AI 编程助手），可以直接让 AI 修改这个系统自身的源代码和样式，把一套通用后台改造成自己想要的业务系统。

项目定位面向**本科毕业设计 / 个人项目**：学生将自己的毕设想法告诉 AI，AI 将基础后台逐步改造成他想要的系统。单人使用，非多人协作产品。

**一句话**：让 AI 帮你锻造自己的毕设系统。

## 2. 项目定位与目标用户

- **目标用户**：本科毕业生（用此做毕业设计）、个人开发者、想快速搭建定制后台的人。
- **使用形态**：单人、本机开发环境使用。用户跑起整套系统，通过网页与 AI 交互，AI 修改源码，热更新实时生效。
- **开放**：MIT 协议开源，代码公开透明。

## 3. Goals / Non-goals / Anti-goals

### Goals（要做的）
- 一个可运行的基础后台：登录 + 系统管理（用户/角色/菜单/日志）。
- AI 定制模块：供应商配置 + 嵌入 OpenCode 界面。
- 进度计划机制：AI 给出分步方案 → 用户确认 → 形成计划 → 每个子功能可点"完成"。
- 节点机制：每个完成的子功能认定为一个节点，记录当时系统状态（git commit + 元数据）。
- AI 能改前端（Vue）、后端（Java）、数据库（自动生成 Flyway 迁移脚本）。

### Non-goals（v1 不做）
- **不做版本回退/丢弃**：节点图 v1 仅做路径记录，点击旧节点只查看，不切换、不丢弃。
- 不做多人协作、租户、复杂数据权限。
- 不做 OpenCode 界面的深度定制（v1 直接 iframe 嵌入官方 Web UI）。
- 不做生产环境部署方案（v1 面向本机开发）。

### Anti-goals（绝对不做）
- 不允许 AI 在没有记录的情况下悄悄改库改代码——每一步都必须留痕。
- 不做让 AI 改动"正在运行的生产系统"的能力。

## 4. 技术栈

| 层 | 技术 | 说明 |
|---|---|---|
| 前端 | Vue 3 + Element Plus | 管理后台 UI |
| 后端 | Spring Boot（v1 单体） | 预留微服务边界，后期可演进 Spring Cloud |
| AI 层 | Node 服务（bridge）+ OpenCode SDK / 官方 Web UI | 托管 OpenCode，iframe 嵌入 |
| 数据库 | MySQL（v1） | AI 改动通过 Flyway 迁移脚本版本化 |
| 构建 | Maven（后端）+ Vite（前端）+ pnpm（bridge） | |
| 许可证 | MIT | |

## 5. 整体架构

```
┌─────────────── Vue 3 + Element Plus 前端 ───────────────┐
│  系统管理                     AI定制                       │
│  用户/角色/菜单/日志            ·供应商配置 ──→ 写 opencode.json
│                              ·进度计划+节点图 ──→ Spring API
│                              ·OpenCode 开发界面(iframe)
└────────┬──────────────────────────────┬──────────────┘
         │ /api (Spring)                │ WebSocket (opencode)
┌────────┴──────────┐        ┌──────────┴───────────┐
│ Spring Boot       │        │ Node bridge           │
│ ·用户/角色/菜单/日志 │        │ ·托管 OpenCode server  │
│ ·进度计划/节点 数据表│        │ ·git 工作区操作          │
│ ·Flyway 迁移管理    │        │ ·应用供应商配置          │
└───────────────────┘        └──────────────────────┘
          │  共享同一个 monorepo 源码目录（本机开发环境）
          └── AI 改这里的代码 → Vite/SpringDevTools 热更新生效
```

**关键设计决策**：OpenCode server 和 Spring 后端操作的是**同一个源码目录**。AI 修改 Vue/Java 文件后，前端 Vite 秒级热更、后端 Spring DevTools 热重载，用户立即看到效果。

## 6. 模块设计

### 6.1 系统管理（v1 精简版，RBAC 基础设施）

- **用户管理**：系统用户增删改查、重置密码、状态启停。
- **角色管理**：角色增删改查、菜单权限分配（v1 只到菜单级）。
- **菜单管理**：菜单/路由的增删改查，驱动前端动态菜单。
- **操作日志**：记录关键操作（登录、增删改）流水。
- **登录日志**：登录成功/失败记录。

（部门、岗位、字典、定时任务等后续版本再加。）

### 6.2 AI定制（项目核心）

**子页面 A：AI 供应商配置**
- 供应商类型：DeepSeek / OpenAI / Ollama / 自定义兼容接口。
- 配置项：API key、接口地址（base URL）、模型名称。
- 数据库连接信息：host、port、database、username、password（供 AI 访问数据库用）。
- 保存后写入 Node bridge 侧的 opencode 配置（并重启 OpenCode server 生效）。
- 安全提示：key 本地存储，明文展示可选。

**子页面 B：OpenCode 开发界面**
- iframe 嵌入 OpenCode 官方 Web UI（方案 A，v1 采用）。
- 通过 CORS + 密码 cookie 完成认证衔接。
- 后续（v2）可升级为自绘 TUI 风格界面（方案 B）。

**子页面 C：进度计划 & 节点图**
- 展示当前进度计划的步骤列表。
- 每步（子功能）带"完成"按钮。
- 节点图：纵向时间线，展示已认定节点。

## 7. AI 改造流程（用户视角）

1. 用户在 OpenCode 界面描述目标（如"改成图书租赁系统，有卖家和买家"）。
2. AI 主动提问澄清需求（如"卖家要哪些功能？商品上架要审核吗？"）。
3. AI 输出**分步开发方案**（如：①卖家创建商铺 ②添加商品 ③商品上架 ④买家搜索 ⑤购物车 ⑥确认订单）。
4. **用户确认方案** → 系统将该方案记录为"进度计划"，生成 `ai_plan` 及各子功能 `ai_plan_item`。
5. AI 依次实现各子功能。
6. 用户实现完某步后，**点击该子功能的"完成"按钮**。
7. 系统认定该步为**一个节点**：git commit 当前全部改动 + 记录节点元数据。
8. 节点图出现新节点（如"功能2 · 添加商品 ✅"）。继续下一步。
9. 全部完成，系统即为用户定制的毕设系统。

**集成深度（v1 决策）**：采用**纯人工记账**模式。
- OpenCode 是一个普通聊天窗口，AI 只负责写代码，对计划表数据结构无感知。
- 计划创建、确认、点"完成"、git commit 全部由人工在界面上操作。
- **AI 与计划的衔接靠提示词**：每次打开/新建 OpenCode 会话时，bridge 自动把当前计划上下文注入到提示中（如"当前进度：第 2 步，做添加商品功能"），让 AI 不至于盲目。
- 后续版本可升级为深度集成（定制 agent + MCP 工具读写计划表）。

## 8. 节点机制（核心数据模型）

```
ai_plan        进度计划     ← AI 出方案，用户确认后生成
  ├─ status: 待开发 / 开发中 / 已完成
ai_plan_item   子功能      ← 每一步，含序号、标题、状态
  └─ status: 待开发 / 开发中 / 已完成 / 已认定节点
ai_node        节点        ← 点"完成" → git commit + 元数据记录
  ├─ plan_item_id  关联子功能
  ├─ git_commit_hash
  ├─ description   功能描述
  ├─ files_changed 改动文件清单 (JSON)
  ├─ migrations    包含的迁移脚本清单 (JSON)
  └─ created_at
```

**"完成"按钮触发流程**：
1. 前端调用 Spring API「认定节点」。
2. Spring 通知 Node bridge 执行 `git add -A && git commit`（提交信息含功能描述）。
3. 拿回 commit hash，连同文件清单、迁移脚本清单存入 `ai_node`。
4. 前端节点图刷新，出现新节点。

**v1 明确不做**：节点回退、节点切换、节点丢弃。git 历史已为后续版本打好底子。

## 9. 数据库方案（Flyway + AI 直接访问）

**决策**：AI 拥有直接访问数据库的能力，但**所有结构变更必须落成 Flyway 迁移脚本**。

**用户视角**：只对 AI 说"加一张商铺表，字段有店铺名、简介、状态"，不接触任何脚本。

**AI 视角**：
1. 通过配置页的数据库连接信息（MCP 工具）直接连接数据库，查看现有表结构。
2. 需要改结构时，自动在 `backend/src/main/resources/db/migration/` 下生成带版本号的迁移脚本（如 `V2__create_store_table.sql`）。
3. 后端启动时 Flyway 自动按顺序应用新脚本，数据库生效。

**运行中如何生效（v1 决策）**：AI 在系统运行中生成新迁移脚本后，依赖 **Spring DevTools 自动重启**——DevTools 检测到 `db/migration` 目录变化自动重启应用，重启时 Flyway 应用新脚本。v1 不做运行时迁移触发接口；若验证发现 DevTools 对 resources 变化的检测不可靠，再升级为显式的"应用迁移"按钮/接口。

**DML 数据写入策略（v1 决策）**：
- 结构变更（DDL）必须走迁移脚本，版本化留痕。
- 测试/业务数据写入（DML，如插测试商品）允许 AI 直接连库操作，不必落脚本；但节点记录中标注"此步含数据变更"。

**为什么落脚本**（对毕设项目关键）：
- 可复现：别人 clone 仓库跑一遍迁移，就能重建数据库，答辩/换机不慌。
- 可留痕：节点记录"这一步动了哪些表"。
- 可追踪：结构变更全部版本化。

**v1 边界**：只记录、不回滚迁移。

## 10. 认证与安全

- 后台登录：Spring Security + JWT（v1 单个管理员账号即可）。
- OpenCode server 认证：官方自带密码认证，配置页填入服务地址和密码，iframe 通过 cookie 免登录。
- API key 本地存储，不上传任何服务。

**目标运行环境（v1 决策）**：以 **Windows 原生**为目标平台（国内本科生绝大多数是 Windows）。bridge 层做平台无关的启动封装；README 将安装 WSL2 作为可选增强项（OpenCode 在 WSL 下运行更稳），但不作为前置要求。

## 11. 仓库结构（monorepo）

```
ThesisForge/
├─ frontend/        Vue 3 + Element Plus 前端
├─ backend/         Spring Boot 后端
│  └─ src/main/resources/db/migration/   Flyway 迁移脚本
├─ bridge/          Node 服务（托管 OpenCode）
├─ docs/            DESIGN.md 等文档
├─ LICENSE          MIT
└─ README.md        项目介绍 + 快速开始
```

单一仓库原因：AI 需要同时改前端、后端、bridge 的代码，一个仓库让改动和节点记录都集中，最简单可靠。

## 12. 开发阶段划分

### 阶段 0：项目骨架
- monorepo 目录结构、README、LICENSE、.gitignore。
- 前端 Vite + Vue3 + Element Plus 空壳；后端 Spring Boot 空壳；bridge Node 空壳。

### 阶段 1：基础后台
- 登录（Spring Security + JWT）。
- 用户/角色/菜单管理，动态菜单。

### 阶段 2：OpenCode 嵌入
- bridge 托管 OpenCode server。
- AI 供应商配置页 → 写配置 → 重启生效。
- iframe 嵌入官方 Web UI，认证衔接。

### 阶段 3：进度计划 & 节点图
- AI 方案 → 进度计划数据表。
- **纯人工记账**：人工在界面创建计划、确认子功能。
- 子功能"完成"按钮 → git commit → 节点记录。
- 节点图前端展示。
- 会话打开时自动注入当前计划上下文到提示词（bridge 侧）。

### 阶段 4：AI 数据库能力
- 数据库连接配置（供 AI 直连查看结构、写测试数据）。
- AI 生成 Flyway 迁移脚本的流程跑通。
- 验证 Spring DevTools 对迁移目录变化的自动重启链路；不可靠则升级显式"应用迁移"按钮。

### 阶段 5：打磨与发布
- README 完善、示例演示、GitHub 发布。
